## How the join works

`city.CountryCode = country.Code` connects each city to its matching country. The columns do not need identical names; their values must satisfy the ON condition. INNER JOIN returns matching pairs. A city with no matching country is excluded.

| Expression | Meaning |
| --- | --- |
| city.Name | City name from the city table |
| country.Name | Country name from the country table |
| city.Population | Population recorded for that city |
| AS CityName | Label for an output column; does not rename the stored column |
| ON | Matching condition between the tables |
| WHERE | Conditions on individual rows |
| AND | Both conditions must be true |
| ORDER BY city.Population DESC | Sort cities from largest population to smallest |
| LIMIT 3 | Return at most three rows |

Use lowercase table names consistently. Table-name case sensitivity can vary by system. Qualify columns such as Population when joining tables that both contain that column.

## WHERE and HAVING

For individual cities, use WHERE, for example:

```sql
WHERE country.Name = 'India'
  AND city.Population > 3000000
```

For groups, filter the calculated result with HAVING, for example:

```sql
GROUP BY CountryCode
HAVING COUNT(*) > 100
```

The learner’s HAVING city.Population > 3000000 query did return the intended four cities in MySQL. It was not a wrong result. WHERE is the clearer, appropriate choice for this row filter. GROUP BY is unnecessary when displaying one row per city without aggregation.

## Query order

Write the clauses in this order: SELECT, FROM, INNER JOIN ... ON, WHERE, GROUP BY (if needed), HAVING (if needed), ORDER BY, LIMIT. Put the semicolon only at the end of each complete statement. A semicolon after WHERE ends that query before later clauses.

LIMIT without ORDER BY gives no guaranteed ordering. These population figures belong to the sample dataset and are not current population estimates.

## Mistakes to remember
